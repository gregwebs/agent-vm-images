# Pi runtime payloads

Pi (`@earendil-works/pi-coding-agent`, default `1.4.0`) and the separate bridge
project (`pi-claude-bridge`, default `0.8.0`) are **reviewed pnpm projects**, not
npm projects. Each carries the same four inputs as dsh — `package.json`,
`pnpm-lock.yaml`, `pnpm-workspace.yaml`, `pnpm-inputs.sha256` (digests of exactly
the first three) — and both are installed by the base-owned pnpm exactly
`11.11.0` with scripts disabled. Neither carries an npm project lock any more.

See `docs/adr/0011-pi-selected-shrinkwrap.md` for the route decisions, the
family-shape and bin-mode reasoning, and the exact limits of the authenticity
claims, and `docs/standard-pnpm-migration.md` for the measured deltas.

## Install contract

`install-pi.sh` (through the composed `run-pnpm.sh` hard envelope) validates the
four inputs, then runs a cold `--prod --frozen-lockfile` install with all five
policy defaults, the npmjs registry, a private HOME/XDG/store and
`--package-import-method=copy`. The reviewed workspaces are byte-frozen:

* Pi: `nodeLinker: isolated`, `hoist: false`, `autoInstallPeers: true`,
  `preferSymlinkedExecutables: true`, `extendNodePath: false`, exactly one
  trust exception (`undici-types@6.21.0`), `allowBuilds: {}`.
* Bridge: `nodeLinker: hoisted`, `autoInstallPeers: false`, the same frozen
  settings, and exactly `ignoredOptionalDependencies:
  ['@anthropic-ai/claude-agent-sdk-*']`.

Hoisted means *no private-store payload*: pnpm 11.11.0 still writes a
metadata-only `node_modules/.pnpm/lock.yaml`, so the installer, the verifier and
the independent oracle all assert that the bridge package is a real directory and
that no directory exists below that store, instead of treating the store's
presence as an isolated tree.

No `--legacy-peer-deps`, no `--no-optional` (pnpm 11.11.0 then reports
`ERR_PNPM_LOCKFILE_MISSING_DEPENDENCY`), no alias workaround, no NODE_PATH and no
source patch. The bridge keeps the SDK **JavaScript**; only its per-platform
native packages are omitted, and Pi loads the SDK through jiti. No second Pi or
`typebox` instance may exist in the bridge tree; peer *declarations* are data.

The project-level `node_modules/.bin/pi` is the reviewed seam and resolves the
locked `bin.pi` (`dist/bundle/cli.js`). Its readlink text is pnpm's business: a
real install links either the public package directory or the resolved
virtual-store instance, so the check that matters is the resolved target (still a
direct symlink inside the payload), not one spelling. `/usr/local/bin/pi` is the static warning
wrapper: a regular file, never a link to the package entry. It enforces
`PI_SKIP_VERSION_CHECK`, requires the mandatory warning and a recognised
first-position subcommand from the per-selection data list
(`dispatch/<version>.txt`, generated by the installer from the bounded installed
help output), and keeps the bridge and Codex extensions as a second and third
explicit `--extension`. Removing or breaking any of them fails closed, and the
`AGENT_VM_PI_NO_BRIDGE` opt-out remains the only supported replacement seam.

The seed hook merges the image Claude executable path into project-owned Pi state
without clobbering user configuration; it is invoked by the caller, never by
Docker CMD. Registration probes are not authenticated session evidence.

## Two independent proofs

* Build-time: `install-pi.sh` downloads every reachable sibling archive
  independently, checks its SRI, extracts it safely and runs the mounted
  build-only `check-installed-bytes.mjs`. Only exactly-derived package-root
  `node_modules/.bin` directories/links are normalised; everything else is
  compared byte-for-byte. pnpm's own `node_modules/.modules.yaml`,
  `.package-map.json` and `.pnpm-workspace-state-v1.json` are metadata, never
  payload: the checker ignores exactly those regular files (a directory or link
  of the same name still fails) because the first real cold install reported them
  as unreachable packages.
* Finished image: `script/test/standard-node-layout.py --consumer pi|bridge`
  reads an extracted virtual root with its own authored expectations (family
  shape, generated bins, wrapper split, hoisted bridge identity, SDK omission)
  and never imports production JS. `standard-image.sh` runs it after extraction.

| Module | Owns | Never owns |
|---|---|---|
| `import-shrinkwrap.mjs` | Authenticated archive data -> an npm-shaped project lock for `pnpm import`, plus the expectation-vs-import delta | Download, npm, YAML or duplicate-key parsing (`recipe-contract pnpm-json`), guessed hashes, an allowlist |
| `archive.py` | Whole-archive preflight and bounded extraction, and the per-invocation rehash of a retained provider tarball | The head-of-line SRI check of a download, any network call |
| `installed-graph.mjs` | Lock-derived instances, dependency and bin-link expectations, non-following inventories, the reviewed family shapes | Reading identity out of `.pnpm` entry names, parsing YAML, trusting an installed link |
| `check-installed-bytes.mjs` | `PREFIX SIBLING EXTRACTED_PACKAGE`: archive-versus-installed bytes, modes and derived links for every reachable sibling | Download, a caller allowlist, deriving expectations from the observed tree |
| `check-runtime.mjs` | genai, protobufjs and (legacy) chord-context esbuild/native probes from the real installed resolution context | Installing, a script fallback, a version-threshold shape guess |
| `prepare-project.py` | The one owning process for a changed/refreshed selection: candidate stage, import or resolve, comparison, pin, frozen validation, four-input publication | Parsing YAML independently, a fallback route, a caller-supplied policy switch |

Reviewed family expectations (independently authored, not derived from an
installed tree): 1.4.0 reaches six members with root-level bins
`core`→`pi-ai`, `ai`→`anthropic-ai-sdk`, `tui`→`marked`; 0.87.0 reaches the
historical five including `chord`→`esbuild` and `core`→`pi-ai`,`yaml`. 1.4.0's
`chord` is published but unreachable and has no `esbuild` dependency.

## Registered catalog (measured, not inherited)

The bridge registers **14** models on the reviewed `0.8.0` payload beside Pi
`1.4.0`, and **11** beside the authenticated legacy `0.87.0` graph (it enumerates
the providers the selected Pi SDK ships); the planning investigation saw 12. The
generic verifier keeps accepting one canonical positive
`AGENT-VM-BRIDGE-REGISTERED models=N` with a non-empty count, and the focused
harness records both measured counts per selection so a change is a review stop.

## Preparation (changed or refreshed selections) — implemented and proven

The changed-selection route is **wired and proven** by the focused harness's real
`--version 0.87.0` leg. `prepare-project.py prepare` decides the route from the
authenticated archive's own content, never from a version number: it queries the
exact selected packument with one bounded `pnpm view` under the owning policy
defaults, downloads the tarball through `download.sh`, checks its SHA-512 against
the registry's `dist.integrity` before extraction, extracts it with `archive.py`,
and then either converts its `npm-shrinkwrap.json` (via `import-shrinkwrap.mjs`
and `pnpm import`) or — when it ships none — resolves the exact selection as an
ordinary all-hashed graph. A download, SRI, extraction, synthesis or fidelity
failure is hard: there is no degraded or range-resolve fallback, and no canned
lock for any version lives here.

Two comparators run on the converted graph and neither may be skipped: the Go
candidate helper with `--shrinkwrap-authority` (which relaxes only the *retained
snapshot* freeze — the archive SRI freeze, manifest/workspace/manager invariants
and closure rules still apply, and no ordinary, adoption or bridge path can name
the mode) and `validateShrinkwrapDelta` against the pre-import expected graph.
Every representation normalisation found is *reported*; none is accepted
implicitly. `reviewed-normalisations.json` holds the normalisations an operator
reviewed for one exact selection (currently the three approved for `0.87.0`, with
their review recorded in ADR 0011), the driver passes that record for the selection
being prepared, and the comparator refuses both a reported normalisation the record
does not name and a record entry this graph no longer produces. A version nobody
reviewed therefore gets an empty record, and anything unexpected stops preparation
before a pin.

`bash images/tools/pi/prepare-lock.sh PREFIX VERSION [--refresh-lock]` and
`bash images/tools/pi/bridge/prepare-lock.sh PREFIX VERSION [--refresh-lock]` are
the stable interfaces; the owning driver is `prepare-project.py`. An equal,
unrefreshed request starts **zero** manager processes (not even `--version`) and
writes nothing. Anything else:

* Pi, selected archive carries `npm-shrinkwrap.json`: synthesize the staged
  project lock from that authenticated archive, run one bounded `pnpm import`,
  compare the graph, then validate frozen and publish.
* Pi, no shrinkwrap: resolve the exact selected version as an ordinary
  all-hashed graph and review the complete delta.
* Bridge, ordinary build: fresh manifest/workspace, no old lock seed. Explicit
  developer refresh (including of the equal selection) seeds the existing pnpm
  lock and reports the full delta.

Publication is one four-input transaction with reverse rollback; status 1 is a
restored failure, 2 usage, 3 an incomplete rollback that keeps the scratch and
prints an absolute recovery path. The temporary npm lock used for `pnpm import`
is unlinked before candidate validation and never committed or copied.

## Upgrades and verification

Upgrade with `bash images/tools/pi/upgrade-pi.sh VERSION` and
`bash images/tools/pi/bridge/upgrade-bridge.sh VERSION`; both publish four inputs
plus one central Dockerfile label in a single sequential transaction. Review
every integrity entry, the selected archive's route (shrinkwrap or not), the
family shape for the new selection, the bridge's unmet peers and SDK omission,
and the per-version dispatch list. See
[CONTRIBUTING](../../../CONTRIBUTING.md#selection-ownership-and-maintenance).

Suites: `bash script/test/pi-prepare-lock.sh`, `pi-install.sh`, `pi-verify.sh`,
`pi-wrapper.sh`, `pi-bridge-install.sh`, `node script/test/pi-shrinkwrap.mjs`,
`node script/test/pi-installed-bytes.mjs`,
`python3 script/test/standard-node-layout.py --self-test`, and the focused
container legs `bash script/test/standard-node-consumers.sh agent-vm-base:local
--consumer pi [--version 0.87.0]` plus
`bash script/test/standard-node-policy.sh agent-vm-base:local --consumer pi|bridge`.
Historical extension compatibility rationale is in the pinned upstream
[bridge ADR](https://github.com/gregwebs/agent-vm/blob/3ec78eebb7bdf743c93942a6ed2e5510de15c52d/docs/adr/0023-image-owned-pi-extension-packages.md).
